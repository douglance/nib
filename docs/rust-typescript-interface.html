How Nib's TypeScript and Rust code connect

They do not share a process. Rust and TypeScript communicate through the portal's HTTP API using JSON. Rust owns the canonical .nib file and rendering; TypeScript owns remote requests, persistence, browser UI, notifications, and optional tmux actuation.

The boundary

Side Owns Interface role
Rust CLI .nib storage, PNG rendering, annotation serialization and merge, CLI fallback behavior Creates a remote review, uploads artifacts, polls for a response, and writes returned annotations into the originating file.
TypeScript server HTTP routes, request state, attachment files, response validation, SSE events, notifications Acts as the workflow coordinator and shared source of remote request state.
React client Inbox, review canvas, comments, decisions, browser-side annotation drafts Reads request JSON and posts a structured human response.

The default transport endpoint is https://nib-global.doug-lance.workers.dev. Cloudflare Durable Objects own request state and R2 owns attachments. Rust can redirect to another deployment with NIB_PORTAL_URL.

The concrete JSON contract

Rust creates a request with kind: visual-review and marks it with the version string nib.visual-review/v1. It uploads two required attachments:

  • image/png with role preview, rendered by Rust.
  • application/x-nib with role canonical, the original file bytes.

The TypeScript server refuses to publish the draft until both attachments exist. A valid response contains a decision, optional comment, and annotation JSON:

{
  "contract": "nib.visual-review/v1",
  "decision": "approve",
  "comment": "Optional note",
  "annotations": []
}

Rust validates the contract version before accepting the response. It then converts every returned serialized annotation back into a Rust annotation and appends it to the local .nib.

Important nuance: the types are mirrored

The interface is versioned, but it is not currently generated from one schema. TypeScript declares RequestRecord, RequestAttachment, and RequestResponse; Rust separately declares the smaller response shapes it consumes with Serde.

That makes the version string and integration tests important. A stronger future boundary would generate Rust and TypeScript types from one JSON Schema, but the present implementation relies on explicit validation and tests.

What is not the interface

  • There is no FFI, WebAssembly bridge, Node native module, or shared-memory channel between the languages.
  • The TypeScript command runner can spawn shell commands, including nib if asked, but that is a generic operator feature rather than the review protocol.
  • TypeScript can write responses into tmux panes for tmux-targeted requests. That path uses the tmux executable, not Rust APIs.
